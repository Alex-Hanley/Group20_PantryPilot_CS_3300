Test Plan for PantryPilot

Version: 1.1  |  Date: November 22, 2026  |  Team: Team 20

1. Introduction

1.1 Overview (Executive Summary)

PantryPilot is a web application designed to help students, roommates, and small households maintain a shared pantry inventory, prevent food waste through expiration tracking, generate constraint-safe weekly meal plans, and reconcile grocery shopping lists.

This test plan evaluates the current MMF 1 (Trusted Pantry Inventory) prototype, a responsive single-page application built with React 19, TypeScript, Vite, and browser localStorage. It also sets out the test strategy for the upcoming multi-tier backend (Java 21, Spring Boot, PostgreSQL, and OpenAI structured JSON planning). Specifically, this document verifies core inventory CRUD workflows, floating-point quantity normalization (roundQuantity), input validation, edit-mode action locking, saved-data validation, browser storage fault tolerance, and the non-HTTPS UUID fallback. It also gives a structured comparison of traditional testing (manual equivalence partitioning, hand-written Playwright E2E scripts, and a manual branch trace) with AI-assisted testing (Claude Code and ChatGPT/GPT-4o).

1.2 Assumptions

  • Runtime & Build Environment: Tests execute on Node.js >= 22.12.0 using Vite 8.3.8 (http://127.0.0.1:5173) and TypeScript 7.0.2 in strict mode.
  • Browser Environment: Automated browser tests execute in headless Chromium via @playwright/test 1.65.1.
  • Storage & Scope: The current release (MMF 1 starter) is a single-browser prototype backed by localStorage under the key pantrypilot.inventory.v1. Multi-user authentication, Spring Security household isolation, and PostgreSQL persistence (MMFs 2–6) are scoped for later sprints.
  • Floating-Point Representation: Pantry quantities are ordinary household measurements normalized to 15 significant digits (Number(value.toPrecision(15))), not arbitrary-precision decimals.
  • White-Box Access Path: src/main.tsx does not export its helper functions, so white-box tests drive specific internal branches through the browser (fault injection, seeded storage, removed browser APIs) rather than calling functions directly. Branch coverage is measured by a manual branch trace (Section 4.3) because no coverage instrumentation is configured for the prototype.
  • AI Tool Governance: All AI-generated test cases were executed against the real codebase, verified for compilation (npm run build) and deterministic pass/fail behavior (npm test), and reviewed by a human developer before inclusion.

1.5 Items Not Covered By These Test Cases

  • MMF 2–6 Backend Services & Multi-User Auth: Expiry triage queues, OpenAI structured meal-plan generation, shopping list reconciliation, waste analytics exports, and Spring Security household isolation are not executed in this cycle because the repository currently implements only the MMF 1 frontend prototype.
  • Cross-Device / Multi-Tab Sync: Concurrent updates across separate browser tabs are out of scope for the localStorage-backed prototype.
  • Visual Regression Across Mobile Viewports: style.css includes a @media (max-width: 600px) breakpoint, but pixel-diff visual regression across iOS Safari and Android Chrome is deferred until staging deployment on GCP Cloud Run.
  • Instrumented Coverage Reports: Automated coverage tooling (V8/Istanbul for the frontend, JaCoCo for the Java backend) is deferred; this cycle uses the manual branch trace in Section 4.3.

2. Quality Control

2.1 Test Plan Quality

  • Requirement-to-Test Traceability: Every test case maps to an explicit MMF 1 acceptance criterion (negative stock prevention, decimal remainder accuracy, edit-mode locking, and persistence across reloads) or to a named branch in src/main.tsx.
  • Adversarial & Fault-Injection Verification: Beyond happy-path flows, the plan requires fault injection: overriding Storage.prototype.setItem to throw QuotaExceededError, seeding malformed or structurally invalid JSON into localStorage, and deleting Crypto.prototype.randomUUID to simulate non-HTTPS LAN origins.
  • Tests Must Detect Faults: Key tests are mutation-checked. For example, removing && i.quantity >= 0 from load() makes WB-05 fail, and restoring it makes it pass.
  • Human Audit of AI-Generated Tests: Every test proposed by Claude Code or GPT-4o must run against the live Vite dev server (npm test), assert both the visible UI and the underlying localStorage JSON where relevant, and pass peer review to remove tautological assertions.

2.2 Adequacy Criterion

Testing for this cycle is complete when all of the following hold:

  • Functional coverage: All 8 core behaviors in README.md (Add, Edit, Search, Fractional Consume, Restore 1, Remove with confirmation, Edit-mode action locking, and Reload persistence) have positive and boundary/negative tests.
  • Structural coverage: Every reachable branch outcome in the state-changing functions load(), newId(), commit(), save(), consume(), adjust(), and the Remove handler is exercised, as recorded by the manual branch trace in Section 4.3. Current result: 37 of 40 outcomes covered; the remaining 3 are unreachable from the UI and are documented as defensive code.
  • Stable, clean build: npm run build (tsc && vite build) completes with zero TypeScript strict-mode errors, and all 32 Playwright tests pass in 3 consecutive runs (observed: 32/32 passed in each of 3 runs, about 4 seconds per run).

3. Test Strategy

3.1 Testing Process

  • Unit & White-Box Testing: Targets internal state transitions, IEEE 754 edge cases (roundQuantity), saved-data schema validation (load()), storage write failures (commit()), and the UUID fallback branch (newId()) in src/main.tsx. Each branch is reached through a controlled browser input and checked against the branch trace (Section 4.3). Once the helpers are extracted into an exported module, they will also be tested directly at the unit level. Backend sprints will use JUnit 5 and Mockito for service-layer rules (such as Shopping List Reconciliation unit conversions).
  • Integration & Persistence Testing (bottom-up): Verifies that React state and localStorage serialization stay in step (commit()): a failed write (QuotaExceededError) must leave the UI, history, and stored JSON unchanged for consume, save, and remove. Backend sprints will use Testcontainers with PostgreSQL to verify Flyway migrations and Spring Data JPA transactions.
  • System / Black-Box Testing: Exercises full user journeys in Chromium via Playwright without inspecting internal code, using accessible roles and labels (getByRole, getByLabel), form submissions, confirmation dialogs, and page reloads.
  • Regression Testing: Every fixed defect (D-1 to D-3) has a permanent regression test, and the full suite is run on every pull request before merge; GitHub Actions will automate this gate in later sprints.
  • Non-Functional Checks: Data integrity under storage failure, safe handling of corrupted data (read-only mode that preserves the raw payload), accessibility of controls via ARIA labels, and suite runtime (about 4 s for 32 tests).
  • AI Tool Integration: ChatGPT (GPT-4o) and Claude Code generated black-box equivalence partitions and adversarial inputs ('Infinity', 'abc', 0.3 - 0.1). Claude Code also read src/main.tsx directly to write white-box specs (restore.spec.ts, load.spec.ts) targeting defensive catch blocks, validation predicates, and floating-point boundaries.

3.2 Technology

  • Playwright (@playwright/test v1.65.1) & Vite (v8.3.8): Browser automation runner configured in playwright.config.ts, which starts the dev server on http://127.0.0.1:5173 and runs headless Chromium tests.
  • TypeScript Compiler (tsc v7.0.2, strict: true): Static type-checking gate executed via npm run build.
  • Browser Evaluation & Fault Hooks: page.evaluate() and page.addInitScript() for localStorage inspection and seeding, Crypto.prototype.randomUUID removal, and Storage.prototype.setItem exception injection; page.on('dialog') to accept or dismiss confirmations.
  • Manual Branch Trace & Mutation Checks: A decision-by-decision table of src/main.tsx (Section 4.3) and hand-applied mutations to confirm tests detect faults.
  • AI Assistants & Planned CI Stack: Claude Code (via the team proxy) and ChatGPT/GPT-4o for test design and generation; JUnit 5, Mockito, Testcontainers, JaCoCo, and GitHub Actions for the upcoming Java 21 / Spring Boot modules.

5. AI Integration and Comparative Analysis

5.1 Overview of AI Tool Impact

Using Claude Code (for white-box branch inspection and Playwright code generation) and ChatGPT/GPT-4o (for black-box equivalence partitioning and adversarial input ideation) cut initial test authoring time by roughly two thirds by the team's own estimates. The AI tools also found IEEE 754 floating-point drift (0.3 - 0.1 and 0.14 + 1) that would otherwise block exact-remainder consumption. Measured by the branch trace, the AI-assisted specs cover 35 of 40 branch outcomes in src/main.tsx, compared with 25 of 40 for the traditionally written specs. Every AI-only test in load.spec.ts came from asking Claude Code to close the gaps the trace exposed.

The AI tools also showed limits that needed human intervention: (1) neither tool tested the non-HTTPS crypto.randomUUID fallback in newId(), because headless Chromium on 127.0.0.1 runs in a secure context, so the bug (D-1) only appeared on a real LAN device; (2) neither initially proposed preserving corrupted saved data (BB-06); (3) early AI-generated locators used unscoped text queries (e.g., getByText('2 kg')) that matched activity history entries until refactored to the Inventory region; and (4) GPT-4o sometimes invented button names (e.g., "Delete" instead of "Remove"). AI suggestions were most useful once a human had supplied the real labels and an explicit coverage target.

5.3 AI Tool Utilization

  • Claude Code (via Team 20 proxy):
    • Features that helped: full-file context across src/main.tsx and playwright.config.ts, so it could match tests to specific branches; it ran the suite itself and fixed failing locators; it wrote consumption.spec.ts, editing.spec.ts, restore.spec.ts, and load.spec.ts.
    • Challenges: early selectors collided between inventory badges and activity history ("2 kg" appears in both); fixed by scoping to getByRole('region', { name: 'Inventory' }). It could not see that a LAN device lacks randomUUID until told.
    • Impact on adequacy and efficiency: given the manual branch trace as a target, it closed the last reachable gaps (save/remove storage failures, schema branches, dialog dismissal), bringing combined coverage to every reachable branch outcome.
  • ChatGPT / GPT-4o:
    • Features that helped: fast requirement decomposition and equivalence partitioning from the README, plus adversarial input lists ('Infinity', blank strings, malformed and schema-violating JSON).
    • Challenges: without access to the code it sometimes invented button names (e.g., "Delete" instead of "Remove"); fixed by pasting the exact aria-label strings from src/main.tsx and running every proposal in Playwright.
    • Impact: broadened black-box input partitions (BB-04) and supplied the payload list for WB-05; did not produce runnable tests on its own.
